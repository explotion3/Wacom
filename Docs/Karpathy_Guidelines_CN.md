# Karpathy 编码准则（中文版）

减少 LLM 编码助手常见错误的行为准则。源自 [Andrej Karpathy 的观察](https://x.com/karpathy/status/2015883857489522876)。

**权衡：** 这些准则偏向谨慎而非速度。对于琐碎任务，自行判断是否严格遵守。

---

## 1. 先想再写

**不要假设。不要隐藏困惑。把权衡摆到台面上。**

动手之前：
- 显式说明你的假设。不确定就问。
- 如果存在多种理解方式，列出来——不要默默选一个。
- 如果有更简单的方案，说出来。该推回去就推回去。
- 如果有什么不清楚的，停下来。说清楚哪里不清楚。问。

---

## 2. 简单优先

**用最少的代码解决问题。不做投机性的东西。**

- 不加没被要求的功能。
- 不为只用一次的代码做抽象。
- 不加没被要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景做错误处理。
- 如果你写了 200 行但 50 行就能搞定，重写。

自问：**"一个资深工程师会不会说这过度复杂了？"** 如果会，简化。

---

## 3. 外科手术式改动

**只动必须动的。只清理自己造成的垃圾。**

编辑现有代码时：
- 不要"顺手改进"旁边的代码、注释或格式。
- 不要重构没坏的东西。
- 匹配现有风格，即使你会用不同的写法。
- 如果注意到不相关的死代码，提一嘴——不要删它。

当你的改动产生了孤儿（无用的 import / 变量 / 函数）：
- 移除**你的改动**导致无用的东西。
- 不要移除改动之前就已经存在的死代码（除非被要求）。

**检验标准：** 每一行改动都应该能直接追溯到用户的请求。

---

## 4. 目标驱动执行

**定义成功标准。循环直到验证通过。**

把任务转化为可验证的目标：
- "加验证" → "写无效输入的测试，然后让它们通过"
- "修 bug" → "写一个复现 bug 的测试，然后让它通过"
- "重构 X" → "确保重构前后测试都通过"

多步骤任务，先列简要计划：
```
1. [步骤] → 验证：[检查方式]
2. [步骤] → 验证：[检查方式]
3. [步骤] → 验证：[检查方式]
```

**强成功标准**让你能独立循环。**弱成功标准**（"让它能跑"）需要不断澄清。

---

## 项目适用说明

这四条准则对本项目（Wacom）的实际意义：

| 准则 | 项目中的体现 |
|---|---|
| 先想再写 | 每个切片先写文档 / 讨论设计，确认后再落代码 |
| 简单优先 | 不引入 GAS / DataTable / ViewModel 等"以后可能用到"的东西 |
| 外科手术 | 修 bug 时只改必要的行，不顺手重构旁边的代码 |
| 目标驱动 | 每个切片有明确验收标准（编译通过 + 测试全绿 + PIE 验证） |

---

## 反面案例（本项目中实际踩过的）

**违反"先想再写"：**
M2 阶段连续盲改 CommonUI 输入问题，没有先诊断根因（PIE 的 Slate 焦点 bug），导致 5 轮无效修改。正确做法：第 2 次失败后停下来，分析根因，换方案。

**违反"简单优先"：**
早期想用 `ConstructorHelpers::FObjectFinder` 在 CDO 阶段加载资产，引入了 bootstrap 顺序问题。`LoadObject` 在 `BeginPlay` 里做更简单、更稳。

**违反"外科手术"：**
修 `ClearLayer` 时写了 `while(GetActiveWidget()) DeactivateWidget()` 死循环——改动范围超出了必要，应该只用快照迭代。
